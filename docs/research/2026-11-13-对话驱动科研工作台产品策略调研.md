# 对话驱动科研工作台产品策略调研

日期：2026-11-13  
对象：DSH Science 产品重构  
结论性质：产品与架构调研，不是实现方案或兼容性承诺

## 结论摘要

建议把 DSH Science 重构为以下三层，而不是把现有全屏工作台简单缩成若干卡片：

1. **对话是控制面和审计入口。** 用户在对话中提出目标、修正假设、批准计划、要求补证据；AI 在同一上下文中解释下一步、报告状态变化并请求必要决策。
2. **按科研项目隔离的结构化状态是真源。** 文章主线、claim、证据、任务、产物、确认回执等仍应由插件后端以稳定对象 ID、revision 和 provenance 持久化。聊天文本不是数据库，卡片也不是第二份业务状态。
3. **卡片是投影与控制柄。** 对话内卡片锚定某次 proposal、decision、result 或 deliverable；右栏卡片展示当前项目状态；语义性修改回到对话，确定性控制可以直接执行，但必须记录决策并通知后续模型请求。

这一方向与 DSH 官方 seam 基本一致：会话使用 append-only `SessionEvent` 日志；Conversation 把持久事件和 transient frames 折叠为节点；右栏是 per-session surface；Goal、Plan、Deliverables、Action Cards 和 Agent Team UI 都从 session/projection 或历史记录派生显示，而不是在 React 组件里另存一份业务真相。证据见下文。

当前 DSH Science 最大的结构性偏差不是视觉样式，而是**状态作用域与交互主次**：主要状态读自 `$DSH_HOME/dsh-science`，`/state` 不要求 session，客户端每 5 秒轮询全量快照；主界面承担导航和流程操作，对话只被当作动作提交渠道。若不先修正项目隔离和状态真源，仅换成卡片 UI 仍会保留跨会话串状态、双真源和陈旧操作等风险。

## 1. DSH 官方如何连接对话、session state、卡片和右栏

### 1.1 SessionEvent 是会话持久化真源

DSH 官方持久化文档明确规定：Session 的 append-only `SessionEvent` 日志是真源；`SessionPersistence` 只为既有事件日志提供 create/open/read/append/flush/close，不再创建一套平行事件类型。这使恢复、重放和派生投影拥有同一条顺序证据链。[本地源码](../../../../research/dsh-repo/docs/subsystems/persistence.zh.md#L5-L11) · [官方仓库固定版本](https://github.com/deepseek-ai/deepseek-harness/blob/fcc0ad462172522aaf5c93a7b2e01f6b9f0b0159/docs/subsystems/persistence.zh.md#L5-L11)

**边界：** 这不等于“所有插件业务状态都必须塞进 SessionEvent”。科研文章的结构化模型可以保存在插件自己的项目存储中，但与对话相关的提案、批准、执行结果和产物锚点应有可重放的 durable evidence。第三方插件还必须确认自己的 event type 是否被当前 Harness 接受，不能只靠 TypeScript declaration merge 假定可持久化。

### 1.2 Conversation 是事件到 UI 的装配层

Conversation 同时接收 durable session events 与 client-only transient live chunks；每个 session 对应一个 assembler。业务通过 `ConversationNodeDefinition` 用稳定 `(kind, id)` 识别生命周期，再按顺序 fold start/progress/end 为不可变状态，最后用 keyed renderer 注入 `conversation.chat.node`。[装配模型](../../../../research/dsh-repo/docs/subsystems/conversation.zh.md#L5-L18) · [定义与 renderer 示例](../../../../research/dsh-repo/docs/subsystems/conversation.zh.md#L173-L245) · [官方仓库固定版本](https://github.com/deepseek-ai/deepseek-harness/blob/fcc0ad462172522aaf5c93a7b2e01f6b9f0b0159/docs/subsystems/conversation.zh.md#L173-L245)

文档特别说明 `match(event)` 是身份提取器而不是业务 fold，并要求跨进程使用生产方拥有的稳定 branded ID。这是科研卡片应以 `claimId`、`taskId`、`artifactId`、`proposalId` 和 revision 为主键，而不是以组件位置或文字标题为主键的直接依据。[身份与 fold 语义](../../../../research/dsh-repo/docs/subsystems/conversation.zh.md#L56-L70) · [详细边界](../../../../research/dsh-repo/docs/subsystems/conversation.zh.md#L248-L254)

### 1.3 同一会话有三类适合科研产品的 UI seam

DSH slot 树已经提供：

- `conversation.composer.context`：适合常驻但紧凑的“当前科研目标 / 阶段 / 阻塞”上下文卡；
- `conversation.chat.node` 与 `conversation.chat.turnTail`：适合提案、批准、执行结果和交付物卡；
- per-session 右栏 slot：适合文章主线、任务、证据、成员和产物的观察/下钻面板。

这些插槽在官方 slot hierarchy 中有明确位置。[Conversation slot 树](../../../../research/dsh-repo/docs/subsystems/slots.zh.md#L136-L185) · [官方仓库固定版本](https://github.com/deepseek-ai/deepseek-harness/blob/fcc0ad462172522aaf5c93a7b2e01f6b9f0b0159/docs/subsystems/slots.zh.md#L136-L185)

右栏本身是 per-session dock：每个 session 有独立 surface，布局可持久化；插件注册静态 tab definition 和 keyed slot body，显示状态放在 slot store，而不是放入全局 React singleton。[右栏语义](../../../../research/dsh-repo/docs/subsystems/sidebar-right.zh.md#L5-L18) · [slot owner/props](../../../../research/dsh-repo/docs/subsystems/sidebar-right.zh.md#L98-L114) · [官方仓库固定版本](https://github.com/deepseek-ai/deepseek-harness/blob/fcc0ad462172522aaf5c93a7b2e01f6b9f0b0159/docs/subsystems/sidebar-right.zh.md#L5-L18)

### 1.4 官方插件给出的可复用模式

#### Goal：结构化状态常驻 composer，但 UI 不另存真源

Goal UI 以 `useProjection('goal')` 读取 persistent goal，在 composer 中显示状态卡和 pause/resume/edit/clear 操作；projection frames 负责刷新，CAS 负责避免陈旧写入。README 明确说 UI 不应拥有领域缓存或平行存储。[Goal UI 本地发布包](../../../../test-env/node_modules/@deepseek-ai/dsh-client-ui-goal/README.zh.md#L12-L52)

**可采用：** 把“当前研究问题、当前阶段、主要阻塞”做成 compact context card，并用 revision/CAS 拒绝陈旧动作。  
**不照搬：** goal 是单对象；文章主线与证据图是多对象、有引用关系的领域模型，不能压成一段 goal 文本。

#### Plan：对话内产物卡 + 右栏审阅 + 独立批准生命周期

Plan UI 在 plan 提交后产生 turn-tail artifact card，自动打开待审右栏；每次提交有独立 tab，历史可恢复正文。计划正文与批准状态是两个生命周期，批准决定是否执行，而“打开/关闭预览”不改变模型状态。[Plan UI 本地发布包](../../../../test-env/node_modules/@deepseek-ai/dsh-client-ui-plan/README.zh.md#L12-L58)

**可采用：** 文献检索方案、实验/分析计划、文章重组提案都应先形成 durable proposal card，再让用户批准、退回或要求修改。  
**边界：** README 也说明 plan mode 是行为引导而非只读沙箱；科研高风险动作仍需后端权限检查和对象 revision 校验，不能只依赖 prompt。

#### Deliverables：产物来自可审计记录，不从最终自然语言猜测

Deliverables UI 从明确的 tool records / present-file events 派生 turn-end 文件卡，并在右栏打开预览；打开文件不会额外启动 agent。README 明确指出不能仅从最终回答文字推断交付物，terminal 创建的文件也需要显式 present 才成为 deliverable。[Deliverables UI 本地发布包](../../../../test-env/node_modules/@deepseek-ai/dsh-client-ui-deliverables/README.zh.md#L12-L39) · [事件与预览](../../../../test-env/node_modules/@deepseek-ai/dsh-client-ui-deliverables/README.zh.md#L67-L76) · [显式交付边界](../../../../test-env/node_modules/@deepseek-ai/dsh-client-ui-deliverables/README.zh.md#L117-L119)

**可采用：** 图、表、论文稿、检索报告和分析结果必须由工具显式登记 `artifactId + path + kind + revision + provenance`，再形成卡片；不要扫描回复关键词或整个工作区猜产物。

#### Action Cards：用户决策是 durable state，执行前重校验

Action Cards 的模型是“模型提出 action → 对话下方出现卡 → 用户明确操作 → handler 检查权限和外部状态 → 记录 decision → 下一次模型请求收到状态变化”。同一 turn 的 pending card 可被替换，执行有 single-flight 和 reconcile，UI 的展开/折叠不会发模型请求。[Action Cards 运行时](../../../../test-env/node_modules/@deepseek-ai/dsh-action-cards/README.zh.md#L12-L64) · [Action Cards UI](../../../../test-env/node_modules/@deepseek-ai/dsh-client-ui-action-cards/README.zh.md#L12-L46)

**可采用：** “批准写入文章主线”“接受图稿替换”“停止成员”“重试失败检索”是确定性 action；按钮提交时必须带 proposal ID/revision，并在执行前重新读取当前状态。  
**不照搬：** 不应把“修改 claim 内容”“改变证据解释”做成静默 CRUD 按钮；这类语义编辑应回到对话，让 AI 展示影响范围并形成新提案。

#### 官方 Agent Team UI：session projection 驱动只读活动面板

官方 Agent Team 的 durable model 是“持久日志，派生状态”：Lead session 记录成员和 task whole snapshots，task 写入使用 revision/CAS；UI 从共享 Session store 读取 `agentTeam` projection，Host projection frames 推送更新。任务板只读，create/update 由 agent tools 执行；打开面板不发请求，UI 不承担 API proxy、状态存储或模型输入。[Agent Team 运行时](../../../../test-env/node_modules/@deepseek-ai/dsh-experimental-agent-team/README.zh.md#L12-L48) · [类型声明](../../../../test-env/node_modules/@deepseek-ai/dsh-experimental-agent-team/lib/types/types.d.ts) · [UI 发布包](../../../../test-env/node_modules/@deepseek-ai/dsh-experimental-client-ui-agent-team/README.zh.md#L12-L54)

**可采用：** 成员/任务活动面板默认观察，控制只保留停止、重试、打开对话/产物等少量明确动作；任务内容的重排和解释通过 captain/root conversation 完成。

## 2. 社区 agent-teams：有价值的产品 seam，也有应淘汰的兼容层

`NanmiCoder/dsh-agent-teams` 不是官方包，但它在缺少完整官方 seam 时实现了较完整的 session-scoped ActivityPanel，可作为迁移参考。

### 2.1 状态模型

`TeamState` 有稳定 team ID、`captainSessionId`、members、tasks、staged/running phase、plan review、approval timestamp、halted/escalated 等显式字段；task 状态也区分 open/claimed/running/completed/failed/cancelled，而不是只给一个模糊百分比。[本地类型](../../../../research/agent-teams/src/types.ts#L163-L309) · [TeamState](../../../../research/agent-teams/src/types.ts#L355-L398) · [社区仓库固定版本](https://github.com/NanmiCoder/dsh-agent-teams/blob/369c2785c473e546124ab1709664058e6ea93948/src/types.ts#L355-L398)

其磁盘真源位于 workspace-scoped `stateDir/teamId/team.json`，同进程写入通过 per-team queue 串行化；inbox 另用 JSONL。[本地状态存储](../../../../research/agent-teams/src/state.ts#L1-L12) · [创建/读写](../../../../research/agent-teams/src/state.ts#L234-L302) · [社区仓库固定版本](https://github.com/NanmiCoder/dsh-agent-teams/blob/369c2785c473e546124ab1709664058e6ea93948/src/state.ts#L234-L302)

**值得采用的不是 `team.json` 文件名，而是作用域：** 状态必须由 workspace/project + root/captain session 身份解析，route 不应返回全局最近一份团队状态。

### 2.2 卡片是 durable anchor，右栏是 live projection

插件用持久的 `agent_teams_create` tool call/result 建立对话卡，stable `callId` 作为节点身份；卡片点击后打开右栏 ActivityPanel。UI 注册 header action、turn-tail summary、右栏 tab 和兼容 overlay，且用 per-session store 记住选择，只有 `captainSessionId` 匹配当前 session 才接纳状态。[客户端装配](../../../../research/agent-teams/src/client/index.tsx#L53-L138) · [对话卡 definition](../../../../research/agent-teams/src/client/agent-teams-card-definition.ts#L161-L215) · [per-session store](../../../../research/agent-teams/src/client/workspace-state.ts#L1-L40)

右栏按当前 session 过滤 live/archive/history，只有当前 session 已挂载且右栏折叠时才自动打开，避免其他会话的后台事件抢占用户界面。[WorkspaceActivity](../../../../research/agent-teams/src/client/WorkspaceActivity.tsx#L28-L133) · [社区仓库固定版本](https://github.com/NanmiCoder/dsh-agent-teams/blob/369c2785c473e546124ab1709664058e6ea93948/src/client/WorkspaceActivity.tsx#L28-L133)

### 2.3 它暴露了一个关键兼容性边界

虽然事件模块注释描述“每次 mutation append captain session event”，实际实现会在 Harness 不认识 out-of-repo event 时省略追加，磁盘状态继续作为权威，且 session event 失败不阻断业务工具。[本地 events 实现](../../../../research/agent-teams/src/events.ts#L1-L59) · [社区仓库固定版本](https://github.com/NanmiCoder/dsh-agent-teams/blob/369c2785c473e546124ab1709664058e6ea93948/src/events.ts#L39-L59)

因此 DSH Science 在实现前必须实测当前 runtime 的自定义 event 写入能力。安全的过渡方案是：

1. 项目存储持有科研领域真源；
2. 使用 runtime 已支持的 durable tool call/result 或官方 projection 记录对话锚点；
3. 卡片从这两类证据重建；
4. 只有验证自定义 SessionEvent 可持久化、回放和 fork 后，才把它纳入正式事件词汇。

### 2.4 不应照搬的兼容实现

Activity monitor 对后端 state endpoint 做需求驱动 polling：有目标时约 1 秒，发现阶段约 5 秒，使用 ETag/304，并在错误时保留最后快照。[本地 monitor](../../../../research/agent-teams/src/client/activity-monitor.ts#L300-L430)

这比无条件轮询更稳，但在已有 Host projection frames 和 native right sidebar 的 DSH 环境中，不应继续复制：

- 全量/高频 polling；
- `window` CustomEvent 作为主要跨组件总线；
- native sidebar 已存在时仍维护全屏 overlay；
- 客户端自己判定业务真源或合并冲突。

## 3. 当前 DSH Science 的实际状态与差距

### 3.1 当前观察

当前客户端注册主工作台、侧栏入口和右栏，并通过 session services 找当前会话；动作函数把自然语言请求送入当前 session 的 submission/prompt queue/steer。这部分已经具备“通过对话执行”的基础。[客户端入口](../../client-src/index.jsx#L1-L90) · [动作提交](../../client-src/workbench/workflow-actions.js#L31-L195)

但业务状态读取是另一条全局链路：

- `useWorkbenchState` 请求 `/plugins/dsh-science/state`，每 5 秒轮询整份 view，错误时保留上次 view；[客户端轮询](../../client-src/workbench/use-workbench-state.js#L4-L31)
- 存储根固定为 `$DSH_HOME/dsh-science`；[全局存储根](../../lib/store.js#L6-L10)
- `/state` 没有 session 参数，读取全局 team、blueprint、figures 等，并以 `process.cwd()` 相关工作区生成响应；[state route](../../lib/httpdata.js#L325-L446)
- 部分状态会 mirror 到 session cwd 下的 `.dsh-science`，但主要 load path 仍是全局目录。[mirror 行为](../../lib/index.js#L182-L210)

**源码事实边界：** 这些路径能证明状态不是由请求 session 显式解析。它们提示多项目/多会话串状态风险，但本调研没有运行并发多会话复现，因此不把“已经发生数据串写”作为已证实故障。

### 3.2 应保留的能力

- 动作先形成自然语言/skill 请求，再进入当前对话，适合继续作为语义变化入口；[workflow actions](../../client-src/workbench/workflow-actions.js#L31-L195)
- blueprint 对部分执行设置 pre-execute confirmation；[确认入口](../../lib/blueprint.js#L670-L690) · [确认工具](../../lib/blueprint.js#L929-L969)
- paper spine 用 semantic hash、revision 和 confirmation receipt 识别修改后失效的确认；[主线确认机制](../../lib/paperspine.js#L31-L78)
- state view 的派生逻辑可以继续作为 server-side read model，但需要按 project/session 输入，不应由客户端各自复制。

尤其应保留 semantic hash/revision：它比普通“已批准”布尔值更适合科研审阅，因为 claim 或证据内容变化后，旧批准不能悄悄沿用。

### 3.3 必须改变的产品假设

现有设计文档把“全功能主工作台”设为 primary surface、对话为补充。[现有重构设计](../superpowers/specs/2026-11-12-科研工作台重构设计.md)

新的目标明确反转了主次：**对话负责意图、解释、决策和推进；UI 只负责观察、下钻和少量确定性控制。** 这不是视觉改版，而是产品信息架构与状态边界的变更。既有文档中的领域对象、确认机制和状态推导仍可复用，但 primary surface 假设不再适用。

## 4. 类似 Agent 产品的官方模式

### 4.1 OpenAI Codex app：chat/project 是工作入口，产物另行检查

OpenAI 官方 Codex app 文档把桌面应用描述为一个可并行运行多个 project、保留多个 chat、管理 files 和 long-running work 的 workspace；用户可以从 chat、project 或 folder 开始，并在同一应用内创建和检查真实输出、安排 chat 内任务。[OpenAI Codex app 官方文档](https://developers.openai.com/codex/app/)

**产品推断：** “conversation as control plane”不要求只剩一个聊天气泡列表；关键是 project/context 先界定作用域，chat 承担意图和过程，真实文件/结果在独立 surface 中检查。DSH Science 可对应为“科研项目 + root session + 文章/产物右栏”，而不是让全局工作台替代对话。

**证据边界：** 公开文档说明产品行为，不说明 Codex 内部数据模型，也不能证明它适合论文证据审计。

### 4.2 Cursor Agent：对话控制长任务，queue/steer 和 checkpoint 分离

Cursor 官方 Agent 文档说明 Agent 位于 sidepane，可独立运行命令和修改代码；复杂工作可以建立 Project，由 coordinator 规划并委派。用户回答澄清问题时，Agent 可继续安全工作并在回答到达后吸收；用户消息可 queue 到后续或 steer 到下一个 tool-call 边界。Checkpoint 在显著修改前自动保存代码库快照，并在 chat timeline 中可预览/恢复；checkpoint 只恢复文件，不恢复消息，且与 Git 分离。[Cursor Agent 官方文档](https://cursor.com/docs/agent/overview)

**可采用：** 区分“排队追加要求”和“立即改变当前方向”；对后台成员采用 steer/queue 的明确语义；重大写入前产生可审阅快照和变更摘要。  
**不照搬：** 科研状态不能用无痕文件回滚替代审计。文章 claim、证据选择和数据处理应产生新 revision，旧版本可追溯；原始数据和已登记分析产物不得由 checkpoint 直接覆盖。

### 4.3 GitHub Copilot cloud agent：session 同时承载 conversation 和 activity

GitHub 官方把 session 描述为与 agentic work 关联的 conversation 和 activity；同一 session 可从提问、规划进入执行，并在支持的客户端之间延续 conversation、context 与 work。Agents panel / Copilot home 汇总 session；进入某个 session 后可查看进度、工具日志等活动，并用 follow-up prompt 纠偏。Copilot 的 commit 可回链 session log，任务完成则以 PR 进入审查。[GitHub Copilot on GitHub 官方文档](https://docs.github.com/en/copilot/concepts/copilot-surfaces/copilot-on-github) · [管理与跟踪 agent 官方文档](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/manage-and-track-agents) · [审查 Copilot 输出](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/review-copilot-output)

GitHub 还把 rationale、confidence 和 approval queue 放在有后果的建议附近，而不是要求用户审核每一步普通推理。[rationale、confidence 与 approvals 官方文档](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/manage-rationale-confidence-approvals)

**产品推断：** 科研任务也应保持“问题 → 计划 → 执行 → 产物 → 审阅”的同一会话谱系；状态卡应回链到发起 turn、计划版本和结果，而不是另开一个失去上下文的任务管理器。

**证据边界：** GitHub 同时存在不同执行后端和保留策略，不能把所有 Copilot session 笼统理解为永久保存。这里借鉴的是可见产品流程，不声称 GitHub 的 agent session 或 review 模型能直接满足论文证据强度、数据不可变性或伦理审批要求。历史上的 Copilot Workspace 用户手册仓库已归档，且 README 将其称为 GitHub Next experiment，因此本调研不把它当当前规范。[Copilot Workspace 历史手册](https://github.com/githubnext/copilot-workspace-user-manual)

### 4.4 Claude Code Projects：协调 conversation、独立 thread 与 Overview 分工

Claude Code Projects 官方文档描述了一个与目标形态接近的产品：持续的 project conversation 充当 coordinator，每项任务可以启动独立 thread；thread 有自己的 session/context，并向协调 conversation 回报。Overview 汇总 threads，并区分 working、waiting on you、finished、PR ready 等注意力状态；项目共享 repository、files、instructions 和 memory，非代码交付物进入 Library。[Claude Code Projects 官方文档](https://code.claude.com/docs/en/claude-projects)

普通 Claude Code session 还支持命名、恢复、分支、切换和导出 transcript；权限模式单独决定哪些操作自动执行、哪些需要确认。[Claude Code sessions](https://code.claude.com/docs/en/sessions) · [Claude Code permission modes](https://code.claude.com/docs/en/permission-modes)

**可采用：** root conversation 负责科研目标和跨任务协调，成员/thread 保留各自 context 与日志，Overview 只做注意力分诊；“待用户输入/待审阅/受阻”应比伪精确进度百分比更突出。  
**证据边界：** Claude Projects 官方标注为 public beta、分阶段开放，不能把其当前 UI 当稳定 API 或通用规范；把 Overview 解释为“卡片系统”是本调研的产品归纳，不是官方术语。

## 5. 建议的目标产品模型

### 5.1 三层状态模型

| 层 | 真源/职责 | 典型对象 | 不应承担 |
|---|---|---|---|
| 对话与 session 事件 | 意图、提案、决策、工具执行、产物锚点和审计谱系 | turn、tool call/result、proposal、decision、deliverable | 直接充当完整文章数据库 |
| 项目领域存储 | 当前科研对象的规范状态，按 project + root session 隔离 | paper spine、claim、evidence、task、figure、artifact、confirmation | 保存 UI 展开/选中等纯显示状态 |
| UI projection / cards | 读取以上两层，展示当前状态并提交带 revision 的动作 | context card、turn card、right-panel card | 自己合并冲突、生成业务 ID、保存平行真相 |

推荐项目身份至少包含：规范化 workspace path、root/captain session ID、稳定 project ID。HTTP route 必须接收当前 session 或由 Host 注入 session context，服务端再解析所属 project；不能信任客户端直接传来的任意磁盘路径。

### 5.2 三类卡片

#### A. Composer context card：我正在推进什么

常驻但折叠，展示：研究问题、当前阶段、下一可执行步骤、阻塞、待用户决策、后台成员数。操作仅保留：继续、暂停、打开项目状态、补充约束。它从项目 projection 读取，不保存业务状态。

#### B. Turn cards：这轮发生了什么

锚定 durable turn/tool record，类型包括：

- proposal card：计划、文章主线改动、图稿替换、证据纳入；
- decision card：批准、退回、要求修改、停止；
- result card：检索/分析/成员任务结果及失败；
- deliverable card：稿件、图、表、数据与报告。

每张卡至少携带 object ID、revision/hash、origin turn、状态、时间、来源/产物链接。卡片显示的是证据投影；删除 UI 卡片不得删除科研对象。

#### C. Right-sidebar project cards：现在项目处于什么状态

按当前 session/project 过滤，提供：

- 文章主线与待确认 claim；
- 任务/成员活动与阻塞；
- 证据和 provenance；
- 图表/稿件/报告等交付物；
- 决策与版本历史。

右栏以观察、筛选、下钻为主。卡片上的“修改”应生成预填的对话请求；只有 approve/reject/pause/resume/stop/retry/open 等确定性操作可以直接调用 handler。

### 5.3 动作协议

所有改变领域状态的动作应遵循：

1. 卡片提交 `objectId + expectedRevision/hash + action + actor`；
2. 服务端重新读取当前对象，校验 session/project scope、权限和 revision；
3. 失败时不做乐观覆盖，返回 stale/conflict 并刷新卡片；
4. 成功时原子写入领域状态和 decision/audit record；
5. 对后续模型工作有影响时，用 follow-up/steer 或下一次 pre-step 通知模型；
6. UI 由 projection 更新，不在本地手工猜测最终状态。

社区 agent-teams 的 approve 流程提供了一个有用边界：先提交 staged plan，再向 captain session 发送 steer；若通知失败，不回滚已经完成的批准。[approve 与 steer](../../../../research/agent-teams/src/index.ts#L375-L405) · [社区仓库固定版本](https://github.com/NanmiCoder/dsh-agent-teams/blob/369c2785c473e546124ab1709664058e6ea93948/src/index.ts#L375-L405)

DSH Science 应进一步把“已提交但模型尚未获知”显示为可恢复状态，而不是把两步伪装成一次不可分事务。

## 6. 分阶段落地建议

### P0：先修正真源和作用域，再改视觉

完成判据：两个不同 workspace/session 同时打开时，状态、卡片、成员和产物不串；陈旧 revision 的按钮会被拒绝。

1. 引入稳定 `projectId` 与 root session 绑定；所有 state/action route 按 session 解析 project。
2. 把当前全局 `$DSH_HOME/dsh-science` 数据迁移为明确的 project-scoped store；迁移过程保留备份和 provenance，不自动猜多个旧项目的归属。
3. 保留 paper spine semantic hash/revision/confirmation receipt，并扩展到 proposal/action。
4. 确认 runtime 实际支持哪些 durable event；未验证的自定义 event 不进入关键路径。

### P1：把主工作台降为“项目观察面”，让对话成为主入口

完成判据：从一个空白对话可发起、查看并推进完整科研任务；用户无需进入全屏 dashboard 才能知道当前阶段或批准下一步。

1. 增加 composer context card。
2. 为 proposal、decision、result、deliverable 注册 turn card。
3. 把现有文章、任务、成员、图表模块迁为当前 session 的 right-sidebar cards。
4. 主工作台若暂时保留，只作为“打开完整项目状态”的二级视图，不再承载唯一控制入口。

### P2：由 polling 迁移到增量投影和可恢复后台工作

完成判据：打开面板不触发 agent；状态变化由 Host projection/event 增量刷新；断线重连可从持久证据重建；后台成员不会抢占非当前 session UI。

1. 用 session projection/frames 替代固定 5 秒全量 polling；短期必须 polling 时至少加 session scope、ETag、可见性/需求驱动和 last-known-good 标记。
2. 加入 live/archive/history 三态和明确的 stale/failure 呈现。
3. 支持 queue 与 steer 的清晰用户语义，避免“发消息”同时承担追加要求和紧急改向。
4. 对重要写入产生变更摘要、影响对象和可追溯 revision，而不是无痕 rollback。

## 7. 可以直接采用与不应照搬的模式

### 可以直接采用

- per-session right sidebar 与 per-session UI store；
- `ConversationNodeDefinition` 的稳定 ID + deterministic fold；
- Goal 的 compact composer context card；
- Plan 的 proposal artifact 与 approval lifecycle 分离；
- Deliverables 的显式登记，不从最终回答猜产物；
- Action Cards 的权限检查、revision/reconcile、decision 记录和模型通知；
- Agent Team 的只读活动投影、工具负责 mutation；
- 当前 DSH Science 的 semantic hash/revision/confirmation receipt；
- 当前 workflow actions 通过 prompt/steer 处理语义变化。

### 不应照搬

- 把聊天文本当结构化科研状态；
- 把 React 卡片本地状态当业务真源；
- `$DSH_HOME` 下唯一全局项目状态，或无 session 的 `/state`；
- 每 5 秒扫描并传回完整工作区状态；
- 同一对象同时由 JSON、SessionEvent 和 UI store 独立修改；
- 未验证 runtime 支持就写自定义 SessionEvent；
- 以任务数量计算伪精确“科研进度百分比”；
- 用 `window` CustomEvent 和全屏 overlay 替代已有 native sidebar/projection seam；
- 对 claim、证据解释、原始数据或已登记分析产物执行无痕 checkpoint 回滚；
- 仅靠 prompt 约束高风险动作，不做服务端作用域、权限和 revision 校验。

## 8. 需要在实现前验证的未确定项

1. 当前 `0.2.2-rc.1` Host 对仓库外 `SessionEventMap` event 的实际写入、持久化、fork 和 replay 行为。
2. DSH Science 现有 mirror 数据与 `$DSH_HOME/dsh-science` 数据在真实用户项目中的归属关系；迁移前不可自动合并。
3. root session、fork session 和 agent member session 应如何共同解析同一个科研 project，同时保持各自 conversation history。
4. 领域状态写入与 session decision event 之间能否使用官方事务/幂等接口；若不能，需要明确 partial-success 状态和补偿流程。
5. 哪些动作属于可直接执行的确定性控制，哪些属于必须形成 proposal 的科研语义变化。建议默认后者，逐项白名单前者。

## 最终判断

DSH Science 不应继续以“科研 dashboard + 对话按钮”为中心，也不应走向“聊天记录就是全部状态”的另一极端。较稳妥的产品是：**对话控制工作，项目存储保存可审计科研对象，卡片把二者连接起来。**

优先级上，先解决 session/project 作用域和单一真源，再把 proposal、decision、result、deliverable 变成对话卡；最后将文章、成员、任务和产物收拢为 per-session 右栏投影。这样 UI 可以显著变轻，同时不牺牲科研工作最重要的版本、证据、确认与 provenance。
