# 对话优先科研卡片工作台重构设计

日期：2026-11-13  
状态：路线 B 与技术设计已确认；待实施与验收  
目标版本：下一个主版本（实施计划确认后定号）

## 1. 意图

DSH Science 要从“固定科研流程页面 + 向对话提交提示词”重构为“对话驱动科研工作 + 卡片投影项目状态”。

用户继续通过自然语言提出问题、补充材料、改变方向和审阅结果。插件负责把长期项目中最重要的论文主线、证据、任务、成员、技能和产物提炼为结构化状态，并在原生对话输入区、对话轮次和右侧栏中显示卡片。卡片帮助用户观察、定位、触发和确认工作，不取代 AI 的推理，也不建立第二套工作流。

概念上，卡片承担 README、HANDOFF 和项目状态摘要的可视化作用；技术上，结构化项目状态是唯一业务真源，README、HANDOFF 和卡片都是它的派生视图，避免自由文本、JSON 文件和 React 状态相互漂移。

## 2. 用户目标与成功体验

目标用户是以论文和科研结果为中心工作的生物研究者。用户不需要理解 skill 名、工具名、session、projection 或状态文件。

成功体验包括：

1. 用户打开一个研究会话即可自然对话；没有论文主线时，原生输入框附近展示“开始探索”“整理已有结果”等技能按钮。
2. 点击技能按钮后，插件使用 DSH 原生 skill 手势准备当前草稿并把输入交还原生对话框；不弹出另一套研究问题表单。
3. AI 在同一轮中完成有意义工作时，把研究问题、Result、证据、任务或下一决策写入项目状态；卡片随持久状态更新。
4. 语义修改通过对话完成。用户点击“修改 Result”时，系统把目标对象带回原生输入框，用户直接说明如何修改。
5. 确认、停止、重试、暂停、打开产物等确定性动作可以直接在卡片上完成，并留下可追溯回执。
6. 右侧栏只显示当前项目最重要的状态、阻塞和下一决策；需要完整关系图或历史时再打开项目总览。
7. AI 可以跳跃、回退、并行和重新规划。阶段是描述，不是阻止思考的向导。
8. 未确认主张仍不能正式派单；该规则由后端执行模块强制，不依赖按钮是否禁用。

## 3. 目标、非目标与反目标

### 3.1 目标

- 对话成为唯一语义输入入口，项目卡片成为可靠的观察和控制表面。
- 研究状态按 project 与 root session 绑定，不同项目、会话和工作区不会串状态。
- 状态写入具有 revision、幂等键、来源定位和明确失败语义。
- 客户端不保存论文、任务或证据的平行业务状态。
- 状态更新使用项目自己的有版本 Remote 流；DSH 会话投影只折叠官方 durable events，不再固定每 5 秒拉取全量状态。
- 复用 DSH 原生 skill、Conversation、Action Cards、Deliverables、Agent Team 和右侧栏 seam。
- 保留 Paper Spine 的语义摘要、版本化确认和确认失效规则。
- 把故障限制在清晰的 module 内，使恢复、测试和迁移可以分别验证。

### 3.2 非目标

- 不把聊天记录当完整论文数据库。
- 不在首版引入通用实验室信息管理系统、样本管理或电子实验记录本。
- 不让 UI 直接编辑任意 JSON 字段。
- 不自动确认核心主张、Result、证据解释或投稿状态。
- 不把任务数量换算成伪精确科研进度百分比。
- 不在本次重构中替换 DSH 的会话、权限、审批、文件预览和 Agent Team 基础设施。

### 3.3 反目标

出现以下任一情况即视为设计失败：

- 用户仍需在插件专用弹窗里重复填写对话已经知道的信息；
- 点击技能按钮只拼接一段自定义提示词，却绕开 DSH 原生 skill 注入；
- 卡片显示的状态与工具实际状态不一致；
- 切换会话后看到另一个项目的数据；
- 断线、重连或刷新导致卡片回退到旧状态；
- 成员结果未经队长整合就自动成为论文结论；
- 卡片上的旧按钮覆盖了更新后的 Result；
- 为追求“自动整理”而在后台静默改写科研主张。

## 4. 已确认路线与备选比较

### 4.1 路线 A：在现有工作台上换卡片

保留全局 JSON、无 session 的 `/state`、固定轮询和前端动作表单，只调整视觉与按钮。

优点是改动小；缺点是状态作用域、双真源、输入焦点和流程僵化仍然存在。删除一个页面后，复杂性会散回各个页面和 HTTP 路由，属于浅 module。未采用。

### 4.2 路线 B：对话优先、卡片投影

对话负责意图、解释和语义变化；项目状态 module 保存可审计科研对象；会话卡和右侧栏从状态、会话事件和现有 DSH 投影派生。技能按钮操作原生输入框，确定性动作经过 revision 校验。

这是用户确认的路线，也是本设计采用的路线。

### 4.3 路线 C：持续解析 README/HANDOFF 生成卡片

兼容性高，但自由文本缺少稳定对象 ID、revision 和冲突语义，容易把措辞变化误判为科研状态变化。保留为导入、导出和交接 adapter，不作为真源。

## 5. 当前实现与必须拆除的假设

当前实现有四个结构性问题：

1. `dataDirOf()` 把主要状态放在 `$DSH_HOME/dsh-science`，各 module 直接读取固定文件名。
2. `/plugins/dsh-science/state` 不接收 session，聚合全局状态与进程工作目录。
3. `useWorkbenchState()` 每 5 秒拉取完整快照，客户端据此重建页面状态。
4. `workflow-actions` 维护多字段表单并向当前 session 提交拼装文本；同名自定义命令还可能遮蔽原生 skill 手势。

重构不是在这些层上再加缓存或卡片，而是替换它们的业务职责：

- 全局文件读取替换为项目上下文解析和项目状态 module；
- 全量 `/state` 替换为会话绑定的轻量投影指针与按 revision 读取；
- 定时轮询替换为投影驱动刷新；
- 动作表单替换为原生输入框 skill 引用和对话上下文引用。

## 6. 产品模型

### 6.1 三层模型

| 层 | 职责 | 权威性 |
| --- | --- | --- |
| 对话与会话事件 | 用户意图、AI 解释、提案、决策、工具执行和产物锚点 | 行为与审计事实 |
| 项目状态 | 研究问题、Paper Spine、Result、Claim、Evidence、确认、焦点和项目元数据 | 科研业务真源 |
| 卡片与总览 | 读取以上两层，呈现当前状态并触发动作 | 无业务写入权 |

团队成员、运行状态和任务板优先读取 DSH Agent Team 投影；文件与交付物优先读取 Deliverables 记录。项目状态只保存跨来源的稳定引用和论文语义，不复制这些系统已经拥有的完整状态。

### 6.2 卡片只支持四类行为

- **观察**：展示当前事实、来源、版本和更新时间。
- **聚焦**：指出待用户输入、待审阅、受阻和推荐下一步。
- **触发**：把 skill、对象引用和建议文字准备到原生输入框。
- **确认**：执行白名单确定性动作，并记录 revision 绑定的回执。

卡片不承担自由文本编辑、任意字段 CRUD、流程排序或隐藏的模型调用。

## 7. 项目身份与 session 作用域

### 7.1 ProjectRef

每个科研项目使用不可变 `projectId`。每次访问由宿主根据 session 解析为：

```text
ProjectRef {
  projectId,
  rootSessionId,
  currentSessionId,
  workspaceIdentity,
  relationship: root | teammate | fork | attached,
  capabilities
}
```

客户端不能提交任意 `projectId` 或磁盘路径来切换项目。Project Remote 请求只提交当前 `sessionId`，宿主验证访问权后解析 ProjectRef。

### 7.2 绑定规则

1. root session 第一次产生持久科研状态时创建或显式连接一个项目；仅浏览卡片、点击技能或普通对话不创建空项目。
2. teammate session 从直接 parent/root 继承绑定，默认可以读取项目和提交任务回报，不能直接修改核心主张。
3. 用户创建的独立 root session 不因为工作目录相同就静默获得写权限；发现同一工作区已有项目时，显示“连接现有项目 / 新建项目”。
4. 普通 fork 默认创建写时复制分支，记录来源项目和 baseRevision，不共享可变状态；只有用户显式 attach 或 merge 才进入同一项目。teammate 必须同时由官方 Agent Team roster 证明，不能只根据 parentSession 推断。
5. 一个工作区可以有多个项目；session 只能有一个当前项目绑定。

一个项目可以绑定多个 root session，但同时只有一个 `captainRootSessionId` 拥有论文语义写权。其他 attached root 具有读取和提案权；切换 captain 必须是显式、带 revision 的 handoff decision，并记录旧 captain、新 captain 和时间。teammate 的权限来自其所属 captain roster，不因连接同一工作区扩大。

普通 fork 的自动 merge 不属于首版。首版只支持隔离分支、只读比较和在尚未分叉写入时 attach；已经分叉后的合并通过显式导出/人工整合完成。后续若需要结构化 merge，单独设计对象映射、确认继承和冲突界面。

### 7.3 工作区标记

工作区 `.dsh-science/project.json` 只保存非敏感的发现信息和 schema 版本，不是真源。它用于恢复提示、迁移和导出；缺失或被复制时不能自动授予写权限。

空白 root session 在打开卡片、点击技能或发送普通消息时不创建项目。第一次成功的持久项目写入才原子创建项目和 captain 绑定。若发现多个现有项目或 legacy 数据导致归属不明确，该写入返回 `needs-binding`，对话仍可继续，但卡片明确提示用户先选择连接或新建。

## 8. 项目状态深 module

ProjectSnapshot 的顶层结构保持稳定，细节沿用现有 Paper Spine v2：

```text
ProjectSnapshot {
  schemaVersion, projectId, revision,
  metadata: { title, workspaceIdentity, createdAt, updatedAt },
  bindings: { primaryRootSessionId, attachedRootSessionIds, branch },
  paper: { question, stage, core, results, narrative, submission },
  focus: { activeResultId, nextDecisions, blockers },
  links: { taskRefs, artifactRefs, reviewRefs },
  decisions: { pending, confirmedReceipts },
  migration: { sourceHashes, migrationIds }
}
```

`paper.results` 继续保存稳定 Result/Claim/Evidence ID、对象 revision、方向、来源定位、允许解释、禁止外推、呈现决策和确认回执。`links` 只保存外部权威对象的稳定引用，不复制 Agent Team task、Deliverable 文件或审查结果的完整载荷。

首版领域词汇以现有 Paper Spine v2 为规范，不另造一套状态：

| 对象 | 核心字段与状态 | 更新与退出语义 |
| --- | --- | --- |
| Research Question | text、scope、revision、source | 语义修改产生新 revision，不覆盖历史 |
| Core | title、claim、innovation、venue、revision、contentHash、confirmation | 不物理删除；语义修改使确认失效 |
| Result | id、title、claim、purpose、status、direction、evidenceState、manuscriptRole、presentation、revision | `planned → in_progress → supported/negative`；退出正文使用 `manuscriptRole=excluded`，`dropped` 只作旧数据兼容 |
| Claim | stable id、text、revision、status | `active/retired`；退休保留历史和证据引用 |
| Evidence | stable id、claimIds、direction、state、sourceLocator、conditions、uncertainty、allowed/prohibitedInterpretation | `planned/observed/verified/disputed/invalidated`；verified 必须有来源定位和允许解释；不物理删除 |
| Decision | proposalId、objectId、objectRevision/hash、status、actor、time、reason | `pending/accepted/rejected/superseded`，已结算记录不可改写 |
| Focus | activeResultId、nextDecisions、blockers | 是可恢复的注意力状态，不等于科学事实或完成度 |

Paper stage 继续使用 `explore/frame/execute/synthesize/draft/audit`，只描述当前主要工作。Readiness 继续从确认、Claim、Evidence、任务、审查、呈现和投稿检查派生，不另存人工百分比。

### 8.1 Interface

项目状态 module 对其他 host 代码只暴露三个主要操作：

```text
resolve(session, actor) -> ProjectRef
read(projectRef) -> ProjectSnapshot
execute(projectRef, ProjectCommand) -> ProjectReceipt
```

`execute` 是唯一写入 seam。它在 module 内完成：schema 校验、角色权限、expectedRevision、幂等、领域约束、事务写入、审计事件和投影通知。页面、工具、命令和迁移代码都不能直接写数据库。

读取支持可选 selector，但 selector 属于 module 实现，不把存储表结构暴露给调用者。

### 8.2 ProjectCommand

不采用任意 JSON Patch。命令使用可枚举的领域动作，例如：

- `project.create`
- `project.attach-session`
- `paper.propose-core`
- `paper.propose-result`
- `paper.update-result`
- `paper.record-evidence`
- `paper.set-focus`
- `paper.confirm-revision`
- `paper.link-task`
- `paper.link-artifact`
- `paper.record-next-decision`
- `project.import-legacy`

每条命令包含：

```text
commandId       幂等键
expectedRevision
actor           session、agent、角色
payload         经 schema 校验的领域参数
provenance      来源 turn、tool call、文件、文献或用户决策
```

批量语义更新使用一个 `ProjectCommandBatch`：一批只有一个 mutationId 和 expectedProjectRevision，内部每个 operation 有稳定 operationId。整批在一个事务中全成或全败，只增加一次项目 revision；每个真正发生语义变化的对象各自增加一次 object revision。业务写入不允许部分成功；唯一允许的 partial-success 是事务已经提交而 outbox 通知尚未送达。

### 8.3 ProjectReceipt

成功、冲突和拒绝使用可区分结果：

```text
applied          新 revision、受影响对象和投影摘要
already-applied  同一 commandId 的原回执
conflict         当前 revision、冲突对象和恢复建议
needs-confirmation
forbidden
invalid
```

调用方不解析错误字符串判断类型。所有用户可见错误由客户端根据结果种类和上下文生成。

### 8.4 存储选择

DSH 0.2.2 要求 Node >=24.9，可使用内置 `node:sqlite`。项目状态采用宿主本地 SQLite，而不是继续组合多个全局 JSON：

- 数据库位于 `$DSH_HOME/dsh-science/science-state.sqlite`；
- 开启 foreign keys、WAL、busy timeout；
- 所有 SQL 使用预编译参数；
- 一次事务同时写入项目事件、最新 snapshot、revision、幂等回执和 outbox；
- 大文件、图像和原始数据只保存受控引用，不写入数据库；
- 凭据、SSH 密码和数据库口令不进入项目 snapshot 或投影。

初版使用“事件表 + 最新 JSON snapshot”而不是过早拆出大量关系表。事件提供审计和恢复，snapshot 提供稳定读取；两者在同一事务提交。提交后由 outbox 推送项目变更，发布失败不回滚已经提交的科研状态，而由 outbox 重试。schema 在 module 入口和读取时校验。后续需要查询特定对象时，可在内部增加索引表而不改变 interface。

### 8.5 确认与并发粒度

项目级 `expectedProjectRevision` 负责防止批量写入建立在陈旧 snapshot 上；确认本身绑定具体对象的 `expectedObjectRevision + expectedHash`。无关 Result 的更新不会使另一张确认卡失效。确认回执保存 objectId、objectRevision、contentHash、confirmedBy、confirmedAt 和 source；对象语义变化才使该回执失效。

卡片 action 同时携带 expectedProjectRevision 与 expectedObjectRevision/hash。若项目 revision 因无关对象改变但目标对象未变，handler 可以重新读取后继续；目标对象 revision/hash 改变则必须拒绝旧卡。

### 8.6 派单硬闸门

正式任务必须显式携带一个或多个 `resultIds`，不能从 active Result 或当前页面推断。执行前重新检查：核心当前 revision 已确认，且每个目标 Result 当前 revision 均已确认。共享任务用同一个 taskId 双向链接全部 resultIds。缺少 resultIds、任一确认过期或目标不存在时，在创建任务序号和外部执行前拒绝。

## 9. 状态写入与自动维护

### 9.1 三类状态变化

1. **确定性事实**：工具创建任务、登记图表、核验 DOI、生成文件。由对应工具 adapter 自动执行 ProjectCommand。
2. **AI 语义整理**：研究问题、核心主张候选、Result 结构、下一决策。由 root agent 在当前轮调用受限的项目更新工具，写入“提案”或非确认状态。
3. **用户决策**：确认主张、接受结构调整、排除 Result。通过对话卡动作或明确的用户消息形成 revision 绑定的决定。

### 9.2 自动更新规则

- root agent 的科研协议要求：当一轮对项目状态产生实质变化时，在最终回答前调用项目更新工具；工具可以批量提交同一 revision 上的一组领域命令。
- 各科研 skill 在其完成判据中说明应写入哪些状态，不依赖最终回答文本解析。
- teammate 只能提交任务回报或状态提案；root agent 整合后才成为 Paper Spine 事实。
- 工具输出、Deliverables 和 Agent Team 已有结构化事件优先；不从最终自然语言猜测文件、任务或完成状态。
- 如果一次由科研 skill 启动的 turn 结束却没有任何项目回执，UI 显示“本轮尚未同步到项目卡”，提供“在对话中同步本轮”入口。首版不额外启动一个静默后台模型来猜状态，避免成本、竞态和错误改写。

首版只对 DSH Science 自带 skill、root/captain 科研协议和本插件工具提供“同轮维护项目状态”的保证。普通自然对话由 root 协议提示在产生实质项目变化时写入；第三方 skill 只有实际调用本插件 ProjectCommand 工具才会同步，未同步时显示上述提示。teammate skill 只能提交提案和任务回报，不能直接写 Paper Spine。

### 9.3 语义强度

- AI 可自动保存候选问题、提案、笔记、待核验来源和下一步建议。
- AI 不能自动把候选改成“已确认”，不能自动提升 evidence verification，不能自动删除历史主张。
- 修改已确认对象会创建新 revision，旧确认自然失效；历史 revision 保留。

## 10. 项目 Remote 流、会话回执与客户端刷新

### 10.1 双层投影

DSH 原生 session projection 的 `init/apply` 只同步折叠 session events，不能异步读取项目数据库。项目状态因此使用独立的、按 session 鉴权的 Remote 流；DSH 原生投影只负责 Goal、Plan、Agent Team、Action Cards 以及工具/命令回执。

项目 Remote 的 frame 只携带客户端需要的轻量指针：

```text
projectId
projectRevision
title
attention counts
activeResultId
updatedAt
changedKeys
operationId
streamFailure?
```

完整 ProjectSnapshot 不放入 Session list summary，也不在每次变更帧中广播。客户端以当前 `sessionId` 建立观察流并读取一致 baseline；之后只在 `projectRevision` 改变或发现 revision gap 时读取新 snapshot。客户端不能传入 projectId 直接寻址。

Remote interface 保持小而明确：

```text
get({ sessionId, knownRevision? }) -> snapshot | not-modified
observe({ sessionId, afterRevision? }) -> baseline | change | reset
act({ sessionId, actionId, expectedRevision, payload }) -> ProjectReceipt
```

`act` 只接受确认、拒绝、暂停、停止、重试等客户端白名单动作，并在内部转为 ProjectCommand；语义变化没有通用 `mutate` 入口，必须回到对话和工具。观察流每个 frame 都带 rootSessionId、projectId、revision 和 generation/cursor 校验信息。

### 10.2 Durable anchor

项目数据库是科研状态真源；对话中的卡片锚点只折叠官方 durable events。项目工具成功结果必须携带标准 `scienceStateReceipt`，Conversation Definition 可以从稳定 tool call/result 重建本轮状态变更卡。命令使用官方 `command/run` / `command/done`；长期待确认操作使用 Action Cards 的 proposal/decision；文件使用 Deliverables。

当前 DSH 0.2.2-rc.1 没有向仓库外插件提供受支持的自定义 durable event 注册面。生产实现禁止直接追加未知 event，也不使用仅限官方 experimental 包的 `appendPluginRecord`。升级 DSH 时可运行负向兼容 spike，但不能把未支持接口放入关键路径。

### 10.3 冷启动与重连

- 首次打开：先建立项目观察 generation，再读取一致 baseline snapshot。
- 变更帧到达：revision 增加才读取；相同 revision 不重复请求。
- 断线：保留 last-known-good 卡片并显示“连接中断，状态可能过期”。
- 重连：建立新的 generation，重新订阅并按 revision 补 snapshot；旧 generation 的响应不能覆盖新结果。
- 发现 revision gap：立即读取 baseline；服务端响应当前 revision，outbox 继续补发遗漏通知。
- UI 不做论文状态的乐观更新。按钮只显示“正在提交”，成功后等待持久回执或新 revision。

## 11. 技能按钮与原生输入框

### 11.1 交互原则

技能按钮是斜杠 skill 的图形入口，不是新的表单系统。

点击“开始探索”后：

1. 从 session-scoped `conversation.input.dock` 使用 `inputActions.captureInsertion()` 捕获带 draft revision 的插入点，再以 `insertText()` 写入 `/sci-hypothesis`，使其成为官方 skill 引用；
2. 如果草稿已有文字，采用明确的保留策略：默认追加 skill 引用，不覆盖用户草稿；
3. 使用 DSH 原生输入生命周期保留焦点、选区、Undo、引用 chip、附件和中文输入法状态，不直接操作 Lexical DOM；
4. 用户继续写“我想研究……”，再使用原生发送按钮；
5. 发送失败时 DSH 原生草稿与附件保留。

`captureInsertion` 与 `insertText` 之间如果草稿 revision 改变，操作明确失败并提示重试，不能整段覆盖新草稿。同名自定义 workflow command 不再注册，避免遮蔽 user-invocable skill。客户端不得复制一份 skill 目录；卡片从 DSH skill registry 的当前目录派生可用性。

### 11.2 两种按钮

| 类型 | 示例 | 行为 |
| --- | --- | --- |
| 语义动作 | 探索、查文献、修改 Result、绘图、写作 | 准备原生草稿并聚焦，由用户发送 |
| 确定性控制 | 确认、拒绝、停止、重试、暂停、打开文件 | 直接执行白名单 handler，携带 revision |

语义按钮不直接发送默认提示，避免误触消耗模型、覆盖草稿或在上下文不足时启动错误工作。

### 11.3 目标对象引用

“修改 Result 2”不会打开 textarea。它把稳定对象引用和一行可编辑引导加入原生草稿，例如视觉上显示 Result 卡片引用，模型收到 `projectId + objectId + revision` 对应的受控上下文。若 DSH 当前引用 codec 不适合第三方对象，首版使用人类可读文字与稳定 ID，并在发送时由项目 module 验证当前 revision。

## 12. 卡片与信息架构

### 12.1 Composer context card

注册在原生 `conversation.input.dock`，位于输入框上方，默认一行，必要时展开。显示：

- 当前项目和 active Result；
- 当前最重要的下一决策；
- 正在运行、等待用户、受阻数量；
- 最近一次持久化时间；
- “打开研究状态”入口。

没有项目时显示轻量起始卡，只提供“开始探索”“整理已有结果”“连接现有项目”。不显示空指标和内部术语。

### 12.2 Conversation turn cards

卡片锚定稳定 turn/tool/action identity：

- 状态变更卡：本轮改变了哪些对象、从 revision 几到几；
- 提案卡：新的文章结构、Result 或证据解释；
- 决策卡：确认、退回、要求修改；
- 结果卡：专家任务或分析的结构化回报；
- 交付卡：复用 DSH Deliverables，不复制文件系统扫描结果。

历史卡片始终显示当时 revision；对象已经更新时标记“已有新版本”，不能继续执行旧动作。

### 12.3 右侧栏“研究状态”

右侧栏是卡片作战室，但用户界面名称使用“研究状态”。它按注意力排序，而不是按固定阶段强迫推进：

1. **待你处理**：待确认、待补充、失败和真正阻塞。
2. **论文主线**：核心结论和 Result 卡，默认折叠证据细节。
3. **正在工作**：成员、任务、依赖和最近活动，读取 Agent Team 投影。
4. **成果**：最近图表、稿件、报告和 PPT，读取 Deliverables 与项目引用。
5. **常用技能**：AI 推荐、最近使用、全部技能。

专家配置通过右侧栏设置入口或项目总览中的独立区域打开，不混入执行状态。

### 12.4 项目总览

保留全屏页面作为二级观察面，适合：

- 大型 Result/Claim/Evidence 关系图；
- 团队 DAG；
- 图表画廊和版本比较；
- 专家与环境配置；
- 决策和 revision 历史。

它不再是开始科研工作的必经入口，不能拥有与右侧栏不同的业务状态。

## 13. 视觉与交互规则

- 以浅色科研排版为默认，深色主题完整适配；一个主强调色，状态色仅表达实际语义。
- 卡片分为 compact、standard、detail 三种密度，不在同一层嵌套多重边框。
- 每张 standard 卡只保留一个主动作；次动作进入省略菜单或展开区。
- 使用“正在工作 / 等待用户 / 待审阅 / 受阻 / 已完成”，只在计算任务有真实进度时显示百分比。
- Result 卡优先显示主张、证据强度、当前缺口和下一决策；内部 ID、hash 和 revision 放在详情。
- 团队成员使用角色图形、活动环和状态文字；颜色不是唯一状态信号。
- 动画只用于展开、状态切换和新回执，120–180 ms，并尊重 reduced-motion。
- 所有动作支持键盘、清晰焦点态和可访问名称。
- 卡片更新不 remount 原生 composer，不触碰其选区、Undo、中文输入法 composition 或附件。

## 14. 确认、权限与科学约束

### 14.1 确认策略

- 探索、文献检索、草拟结构、提出 Result、讨论写作不要求确认。
- 正式团队派单要求核心和目标 Result 当前 revision 已确认。
- 修改已确认语义后，旧确认失效；派单检查在 ProjectCommand 执行时重新计算。
- 确认卡显示对象摘要、revision、主要变化、证据缺口和确认后允许的动作。
- 卡片点击只提交确认意图；handler 重新读取对象并校验 revision，陈旧时拒绝并打开新版本。

### 14.2 角色隔离

- root/captain 可以提出和整合论文语义，用户确认后执行正式派单。
- teammate 可以写任务状态、结果提案和产物引用，不能确认核心或直接覆盖 Paper Spine。
- expert skill 安装是 host/global 配置；项目只保存“该项目启用了哪些能力”的引用。
- SSH、数据库和外部上传继续使用宿主审批；项目卡不能扩大原有权限。

## 15. 错误与恢复模型

错误必须回答四件事：发生了什么、是否已持久化、用户能做什么、重试是否安全。

| 场景 | 持久化语义 | UI 恢复 |
| --- | --- | --- |
| 草稿插入失败 | 无项目改动 | 保留原草稿，提示重新选择技能 |
| 提交被宿主拒绝 | 无项目改动 | 原生 composer 保留内容 |
| revision conflict | 无覆盖 | 刷新卡片，显示新旧差异并回到对话 |
| 项目写入成功、模型通知失败 | 项目已更新 | 标记“已保存，AI 尚未获知”，提供重新通知 |
| 投影更新失败 | 数据库可能已更新 | last-known-good + 明确 stale 标记，按 revision 补读 |
| 数据库校验失败 | 事务回滚 | 隔离损坏记录，项目进入只读恢复模式 |
| 成员任务失败 | 不改变论文主张 | 工作卡显示失败与重试/重新规划入口 |
| 迁移歧义 | 不自动导入 | 显示来源文件与目标项目选择 |

所有跨两步操作保存明确的 partial-success 状态，不用“整体失败”掩盖已发生的写入。

## 16. 旧数据迁移

### 16.1 原则

- 迁移前对旧 `$DSH_HOME/dsh-science/*.json` 和工作区 `.dsh-science` 生成只读清单、hash 和备份。
- 旧数据归属明确时展示导入预览；归属不明确时由用户选择项目，不按当前 cwd 猜测。
- 每个迁移使用稳定 migrationId，重复执行返回原回执。
- 迁移成功后旧文件保留为只读备份，直到用户明确清理。
- 不做双写。一个项目完成 cutover 后，只通过新 module 写入；旧 adapter 仅供读取和导入。

### 16.2 兼容期

插件检测到旧状态但新项目尚未建立时，右侧栏显示“发现旧研究状态”，提供预览和导入。原有主工作台可以在一个版本内作为只读 legacy 入口，不能继续修改旧文件。

README 与 HANDOFF 在首版不自动物化，避免覆盖用户手工维护的文件。项目总览提供显式“导出项目摘要/交接记录”动作，用户选择目标路径后生成带 revision 和时间的文档；已有同名文件默认生成新文件或要求确认，不静默覆盖。自动持续导出属于后续可选能力。

## 17. Module 划分

### Host

- `project-context`：session、root、workspace 与 project 绑定解析。
- `project-store`：SQLite、事务、schema、revision、幂等和恢复。
- `project-domain`：ProjectCommand 领域约束和 snapshot 派生。
- `project-tools`：把 AI 工具参数适配为 ProjectCommand。
- `project-remote`：按 session 提供 snapshot/change/reset、历史与迁移预览，不接受客户端自报 projectId。
- `project-outbox`：提交后变更发布、重试和 partial-success 恢复。
- `session-receipts`：只折叠官方 tool/command/action-card durable events，生成对话卡锚点。
- `legacy-import`：旧 JSON 只读识别、预览和导入。
- `conversation-cards-host`：Action Card kind、确认 handler 和模型状态通知。

### Client

- `project-binding`：以当前 session 订阅项目 Remote 流并维护 generation、baseline 和 revision gap 恢复。
- `skill-launcher`：原生草稿插入、冲突策略和可用性。
- `composer-context-card`：输入框上方摘要。
- `turn-cards`：状态变更、提案和决定。
- `research-sidebar`：研究状态卡片作战室。
- `project-overview`：关系图、DAG、成果和设置。
- `card-system`：有限的卡片布局、状态与动作原语。

页面只调用这些 module 的 interface，不直接访问 HTTP 路径、SQLite 表、全局 JSON 或 DSH 内部对象。

## 18. 低缺陷设计约束

1. 单一写入 seam：所有项目 mutation 经过 `execute`。
2. 单一文本入口：所有自由文本经过 DSH 原生 composer。
3. 单一 revision：整个项目有单调 revision，每个语义对象另有自身 revision。
4. 幂等优先：每次用户点击、工具调用和迁移都有稳定 commandId。
5. 后端重校验：按钮禁用只是提示，权限、确认和 revision 在 host 再检查。
6. 无平行真源：React state 只保存展开、筛选、选中和 pending 等显示状态。
7. 无静默合并：冲突必须返回 conflict，用户或 AI 在对话中解决。
8. 有界载荷：投影只传摘要，详细证据和历史按需读取。
9. Last-known-good：读取失败不清空正常卡片，但必须标记 stale。
10. Replace-don't-layer：新状态链路通过验证后替换旧链路，不在旧 `/state` 上叠更多同步逻辑。

## 19. 技术 spike

正式实施计划前完成四个最小 spike；spike 只验证 seam，不保留产品代码：

1. **原生 skill 草稿**：从第三方卡片把一个 user-invocable skill 插入当前 DSH composer，验证现有草稿保留、skill chip、焦点、中文输入法、Undo 和发送失败恢复。
2. **项目 Remote 流**：注册最小 get/observe 流，验证一致 baseline、增量刷新、revision gap、重连、fork、plugin reload 和 outbox 补发。
3. **durable receipt**：用官方 tool call/result 或 command/action-card 事件重建本轮回执卡；把未知 event 与 `appendPluginRecord` 的拒绝固化为负向兼容测试。
4. **项目绑定**：两个 root session、一个 teammate、一个 fork 和两个 workspace 的隔离矩阵，验证继承、连接和拒绝路径。

spike 的输出是事实记录和选定 adapter，不是功能实现。

## 22. 设计调用与待技术验证项

### 本设计已经作出的调用

- 对话是主入口，完整工作台降为二级总览。
- 技能按钮准备原生草稿，不直接发送模型请求。
- 语义修改进入对话，确定性动作才直接执行。
- 项目状态使用 Node 内置 SQLite 事务存储。
- 客户端只通过 session 解析项目，不信任客户端 projectId 或文件路径。
- teammate 结果是提案，root/captain 是论文语义的单一写入者。
- 首版不增加静默后台“总结模型”；由当前 root agent 与结构化工具同轮维护状态，并显式暴露未同步回执。
- 旧数据只读导入，不双写。

### 待 spike 决定、但不改变产品行为的技术项

- `inputActions.captureInsertion/insertText` 在卡片按钮上的焦点保留、追加分隔和失败提示细节；
- 项目 Remote 的具体 typert 注册与 baseline/change/reset cursor 形状；
- 官方 tool/command/action-card receipt 在 Conversation Definition 中的最小稳定字段；
- fork 绑定选择卡使用 Action Card 还是一次性 composer context 交互。

这些选择必须以当前 DSH 0.2.2-rc.1 的实际运行结果决定，不能凭类型声明假定可用。
